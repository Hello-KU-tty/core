## 제품 합격 기준

- 사용자는 Kiro editor **한 창**에서 Discovery→Spec→실제 Builder 작업을 진행한다. Builder가 생성 workspace에서 코드·테스트를 수행하고 Core의 Task·Decision·Context·Completion을 실제로 갱신한다.
- Builder가 ACTIVE인 임의 시점에 사용자가 새 질문을 보내면, Helper가 그 순간의 Task·Decision·코드·Evidence에 관한 맥락을 제한적으로 읽고 **Builder terminal 전에** 화면에 답한다. Builder는 그 뒤에도 실행·Core mutation 도구를 잃지 않고 완료한다.
- Helper와 Analyst는 write/shell/State mutation을 실행할 수 없다. 읽기는 Core가 묶은 맥락만이어야 한다는 전제까지 강요하지 않는다. 다만 현재 Project W와 관련된 필요한 코드·상태로 제한해야 하며 W 밖의 임의 파일·secret 읽기는 허용하지 않는다. Agent prompt의 자제만으로 이 경계를 증명하지 않는다.
- Agent 작성 설명과 합성 USER Evidence를 구분하고, Episode 단위 Analyst 제안·Core의 보수적 Concept State 처리·다음 개인화·동작하는 결과물까지 이어져야 최종 제품 PASS다.
- Model turn 성공, 병렬 tool 동작, 단일 Host 결과, 전체 제품 계약을 별도 판정한다. 이전 두 창 실측은 구조적 우회 결과일 뿐 이번 한 창 합격이 아니다.
- 새 goal의 Discovery→Spec lineage, 최신 코드·Decision을 반영한 Builder, Builder 도중 나중에 입력한 Helper 질문과 독립 입력·조기 답변, 사용자 이유가 붙은 실제 Decision 선택과 구현 반영을 연결해 검증한다.
- 합성 USER 입력의 provenance를 표시하고 Episode Analyst 제안과 Core Evidence 수락·기각을 분리한다. 그 근거가 다음 Helper 답변과 추천에 실제 반영되는지, 결과물이 실행되는지, 오류·취소 뒤 복구되는지도 확인한다.

## 첫 판별 질문

2026-09-14의 DAG probe는 같은 W windowId=4에서 두 MCP 서버 `tools/list`까지 확인했으나 `orchestrate_subagent`/child action이 없었다. 이는 **모델이 호출하지 않았는지, 도구가 catalog에 없었는지 미분리** 상태다. 현재 설치본 전체의 IDE-only 가능성을 부정하는 근거로 사용하지 않는다. 우선 native session의 실제 custom-Agent tool ID catalog와 종료 stopReason, 원문을 저장·표시하지 않는 `DAG_TOOL_UNAVAILABLE` 정확 sentinel boolean, Agent mode, MCP readiness를 계측한다. 이를 통해 feature flag 미활성, prompt 무시, action 전달 누락을 분리한다. 기존 모델 원문을 사후 추측하지 않는다.

같은 세션에서 `orchestrate_subagent`가 비활성이라도 `invoke_sub_agent`의 한 모델 응답 안 다중 tool dispatch가 병렬인지 설치 source로 확인한다. Built-in ChatAgent의 별도 실행 queue가 실제 최소권한 Helper 경로가 될 여지도 재검토한다. 이때 tool이 목록에 보이는 문제와 **실제 실행 권한 및 credential 노출**을 분리해 판정한다. MCP call의 비모델 `_meta`에 신뢰할 수 있는 originating session/role이 들어가면 stable broker가 server 측에서 mutation을 거부할 수 있는지 조사한다. 없다면 같은 Builder bearer를 볼 수 있는 Helper를 prompt/승인에만 맡기지 않는다. Kiro 공식 Focus/세션 기능이 동일 사용자 창 안에서 통제하는 내부 경로도 실제 queue/MCP 경계로 검증한다.

기존 subagent 후보의 `subagent_response.files`→parent 직접 임의 절대 경로 read는 현재 adapter에서 실제 위험이다. 과거 문서의 **Core-context-only** 제한은 제품 브리프보다 좁지만, W 밖 읽기 금지는 제품의 최소권한·local-first 원칙에서 나온다. 새 경로가 child file handoff를 제거하거나 W-root를 실제로 강제하는지 확인하기 전에는 제품 Helper PASS를 주장하지 않는다.

설치 source에서는 IDE primary session의 `clientMeta.settings` 구성에 `subagentOrchestration`가 포함되지 않아 현재 버전의 DAG 도구는 미노출일 가능성이 높다. 단, 이전 probe는 정확한 runtime catalog를 기록하지 못했으므로 실제 도구 부재라고 단정하지 않는다. 동일 source의 일반 ToolUse dispatcher는 한 모델 응답의 tool promise를 먼저 시작한 뒤 완료를 기다린다. 그래서 stock 경로의 `invoke_sub_agent` 두 호출이 실제로 같은 응답에서 겹칠 수 있는지, 새 고유 token-free profile과 45초 barrier로 판별한다. 이것은 병렬 기능 판별일 뿐 제품 경계 증명이 아니다. 기존 DAG probe의 profile·marker·결과는 보존한다.

MCP wrapper는 모델이 넣은 `_meta`를 제거한 뒤 공용 client에서 `callTool(name,args)`를 호출하므로 해당 callback에 신뢰할 수 있는 originating session/role이 보이지 않는다. Built-in ChatAgent에 Builder bearer를 보여 주는 경로는 현재 자료로 허용하지 않는다. Kiro의 session-scoped hard deny가 실제로 서버 실행과 직접 도구에 적용되는지 별도 확인할 가치는 있다.

## 단일 창 후보의 현재 순서

1. **Stock `invoke_sub_agent` 다중 호출:** 설치본의 ToolUse dispatcher는 같은 모델 응답에서 각 도구 promise를 시작한 다음 await한다. token-free child A/B를 별도 45초 barrier에 보내 실제 병렬성을 확인한다. 부모 native turn 180초 상한이며 Core credential이나 앱 파일 변경 도구를 probe에 넣지 않는다. 새 `vibe-single-invoke-*` profile과 `single-host-invoke-probe-*` marker는 과거 DAG 실험과 독립이다. 단, child `subagent_response.files`는 tool handler가 실패해도 parent가 읽는 우회가 소스상 확인되어 있으므로 이 route의 제품 bounded-read 경계는 아직 해결되지 않았다.
2. **한 endpoint의 H cwd built-in ChatAgent Helper:** W에 열린 Kiro mux에 `session/new(cwd=H)`를 Builder보다 먼저 생성하고 `mode=vibe`로 둔다. built-in ChatAgent의 즉시 실행 queue가 W custom Builder와 병행 가능한지 확인한다. H는 이미 승인된 runtime/workspaces 내 private directory이고 새 editor 창이 아니다. MCP pool은 공유되므로 H의 정책이 Builder MCP·native file/shell을 실제로 거절해야 한다. Kiro 공식 [capability permissions](https://kiro.dev/docs/ide/whats-new-v1/permissions/)에 따르면 deny가 모든 scope의 allow에 우선하고 workspace 규칙은 사용자 로컬 `~/.kiro/workspace-roots/<hash>/permissions.yaml`에 있다. 하지만 설치본의 filesystem workspace rule은 H 아래 대상에만 match하므로 H 파일만으로 W·외부 절대 경로를 하드 거절한다고 가정하지 않는다. `_kiro/permissions/explain`으로 H/W/외부 `fs_read`·`fs_write`, shell, MCP, subagent 등을 **모델 없이** 판별한다. ASK면 검증된 session-scoped `reject_always` 가능성을 별도 판별하고, ALLOW/불명확이면 Helper prompt를 금지한다. `_kiro/policy/check`는 ASK 시 실제 permission request를 만들 수 있으므로 초기 읽기 전용 검사에 사용하지 않는다.
3. **역할 반전 built-in Builder + custom Helper:** custom Helper tool catalog를 read-only로 만들고 W built-in Builder의 즉시 실행을 이용할 수 있다. 그러나 built-in Builder native fs_write/shell을 W 전체 정책으로 거절하면 기존 생성 앱 구현 수단도 사라진다. 범위를 묶은 IDE-issued executor를 추가해야 할 수 있어, 현재 H Helper보다 큰 아키텍처 변경이다. callback만으로 ALLOW된 native 도구를 막을 수 있다고 주장하지 않는다.

각 route의 queue 병렬성, 권한 정책, 제품 전체 흐름은 서로 다른 판정이다. 첫 route의 barrier 결과만으로 Helper bounded read나 Discovery→다음 개인화까지의 제품 PASS를 쓰지 않는다.

이후 source review에서 session `all deny`만으로 제거 여부를 알 수 없는 조건부 native 도구와 모델 turn 바깥의 command hook을 추가로 찾았다. 모델을 재개하기 전, 설치된 Kiro의 read-only experiment command로 `agentArtifacts=false`, `taskTracking=false`를 요구하고, 동일 extension-host process에서 screenshot port와 모든 remote tool 로드 override가 꺼져 있는지 확인한다. 첫 무모델 feature 검사에서 실제 UI는 `artifacts=UNKNOWN tasks=UNKNOWN screenshot=OFF remoteAll=OFF safe=false`였으므로 pair/model을 실행하지 않았다. 동시에 W panel의 `hostPid=12085`가 Kiro window4 extension-host 로그에서 Kiro Agent와 panel이 함께 활성화된 같은 PID와 일치해 환경 변수 조회의 동일 프로세스 전제는 실측했다. `UNKNOWN`의 원인은 설치 Kiro stable 채널이 `visibility:'insider'`인 두 feature를 `getExperiments` 응답에서 숨기는 구조다. 실제 도구 생성에 쓰는 `RE.isEnabled(key)`는 정의가 보이지 않으면 false를 반환한다. 이에 격리 검사기는 설치 IDE/Agent 버전을 핀하고, `vscode.env.buildQuality`가 정확히 stable/rc이며 command가 성공해 **빈 plain object**를 반환할 때만 두 feature를 OFF로 해석하도록 좁혔다. 다른 누락·오류·비정상 응답은 여전히 실패한다. 수정 후 무모델 재검사 결과가 나오기 전까지 모델은 계속 보류한다.
재검사에서는 panel 확장에 허용되지 않은 proposed `vscode.env.buildQuality` API 접근이 Kiro의 modal 오류를 일으켜 feature 응답 전에 중단됐다. proposed API 권한을 추가하지 않았다. 설치 source에서 공개 `vscode.env.appRoot`는 제안 API 검사 없이 현재 앱 root를 반환한다. Kiro main은 그 root의 `product.json`을 읽어 product service와 extension-host init의 `quality`로 전달하고, Kiro Agent 전용 proposed getter도 그 init 값을 읽는다. 수정한 검사는 앱 root와 product 파일의 canonical 경로, 제품 버전·VS Code 버전·commit·`quality=stable`, override 파일 부재, Agent extension 버전, 성공한 experiment command의 정확한 빈 객체를 함께 요구한다. 이 결합이 성립할 때만 설치본 `RE.isEnabled`의 invisible-definition=false를 적용한다. 이 수정도 다음 UI 검사 전까지 source·자동화 검증 결과일 뿐이다.

이 수정 후 실제 Inspector UI는 `artifacts=OFF tasks=OFF screenshot=OFF remoteAll=OFF quality=stable safe=true`였고 `hostPid=16738`은 window4 extension-host 로그의 Kiro Agent와 panel이 함께 활성화된 PID와 일치했다. 이어 실행한 **무모델** H pair 점검은 `NATIVE_H_CATALOG_BUILTIN_SHELL`로 실패해 모델을 시작하지 않았다. 설치 source를 좁혀 보니 all-DENY 이후에도 `shell` tag가 남는 이유는 `list_processes`와 `get_process_output`이 capability mapper에 없기 때문이다. 이 둘은 H session/new마다 새로 만든 빈 process-manager map만 열람하며, Builder W의 process manager나 외부 프로세스에 연결되지 않는다. 실제 명령 실행·프로세스 제어 도구는 `shell` capability로 매핑되어 제거된다. `_kiro/tools/didChange`는 도구 ID가 아닌 category만 제공하므로 이 결론은 **고정 설치본의 전체 shell-tool source inventory, session-scoped map, policy deny, 동일 프로세스·기능 플래그**를 함께 확인한 범위에만 적용한다. 격리 gate를 유일한 `builtin shell` tag 한 개, 다른 builtin·MCP tag 0개로 좁혀 수정했으며 H tool call은 여전히 모두 중단한다. 이 시점까지 수정 후 pair 결과는 재실측 전이었다.

그 뒤 부모/평가자가 W만 reload해 같은 창에서 Inspect를 재검사했다. 모든 feature/env flag가 OFF·quality stable·safe=true였고 표시 PID 18570은 Kiro Agent와 panel이 함께 활성화된 새 extension-host 로그 블록과 일치했다. 이어진 **무모델** H pair UI는 `PREFLIGHT_PASS window=4 sessions=2 memoryDefaults=true denyAll=true catalogSafe=true shellIntrospectionTags=2 analystHaiku=true modelTurns=0`였다. 이는 수정한 source-pinned 보호 세션 사전 점검의 실제 PASS이며 H4 Analyst가 응답할 수 있다는 기능 PASS는 아니다.

부모가 저장된 E Episode의 Analyst 재시도를 UI에서 한 번 시작하자, worker는 두 차례 모두 약 1초의 H native turn 뒤 `NATIVE_H_UNEXPECTED_TOOL_OTHER`로 fail-closed했다. 첫 claim 17:45:29 UTC, 두 번째 17:45:34 UTC이며 이번 실패는 30초 lease 만료나 JSON schema parser 단계가 아니다. ACP `tool_call`/`tool_call_update`가 있었다는 것까지 확인되지만 기존 `_meta.kiro.toolId` 분류는 builtin action에 항상 존재하지 않아 정확한 도구 ID를 특정하지 못한다. 표시 title이나 모델 텍스트로 권한을 판단하지 않는다. 격리 진단은 ID 누락과 알려지지 않은 ID를 별도 고정 코드로 분리했으나 다음 UI turn 전까지 적용 효과는 미검증이다. 기존 실패 Episode·Core 상태는 보존한다.

이후 **소유 H session ID와 정확한 workspace hash의 Kiro session store만** 읽는 metadata 검사에서 두 재시도의 원인을 `fetch_cloud_config`로 특정했다. 이는 모델이 선택한 도구가 아니라 설치본이 `session/new`에서 비동기로 시작하는 deterministic action이다. 두 저장 기록은 각각 `tool_call`/`tool_result`가 `completed`/success였고 결과 객체는 `kind=notEnabled,retracted=false`였다. ACP 알림 후 abort는 이 action의 실행을 막지 못했다. 결과 객체 하나만으로 안전하다고 판단할 수 없는데, 기존 cache의 retraction 실패도 같은 `retracted=false`가 될 수 있기 때문이다. 이번 host의 cloud config root 자체가 ENOENT였고, 설치 source상 빈 상태의 `notEnabled`는 download·delete·consumer rescan을 하지 않는다. 과거 W의 **모델 없는 다른 저장 세션**에는 완료쌍 여러 개가 누적돼 있었다. 이를 이번 새 RPC의 소유 세션이나 재실행 원인으로 단정하지 않는다.

격리 구현에는 H Helper·Analyst와 no-model marker, product W Discovery·Builder 각각의 `session/new` 뒤 **같은 소유 session의 action terminal barrier**를 추가했다. Kiro의 workspace-path SHA-256 hash와 session ID를 사용해 정규 파일·소유 UID·`session.json`의 단일 root를 검증하고, bounded JSONL에서 모든 cloud call/result가 연결·성공·무변경인지 확인한다. 이번 `session/new` 호출 시작시각 이후 완료쌍이 있어야 하므로 오래된 완료 기록만으로는 통과하지 않는다. cache root는 전후 ENOENT, model-turn이나 다른 action은 실패한다. H는 완료 뒤 권한·hook·catalog·memory·feature flag를 다시 확인하며, W는 완료 뒤 같은 observer 소켓의 mode-select RPC를 수행한다. 이 변경은 focused 45/45, typecheck·bundle build·lint·format을 통과했지만 **실제 UI pair/Analyst 재시도 전**이므로 효과는 아직 미검증이다. 기존 all-tool abort는 유지한다.

H-first 순서도 좁혔다. H model prompt가 이미 진행 중이면 Builder의 W `session/new`와 새 H pair/marker 생성은 그 prompt 종료까지 bounded·abort-aware로 기다린다. Builder가 먼저 opening intent를 기록한 경우 H는 prompt 직전에 이를 다시 확인해 W 준비가 끝날 때까지 기다린다. 대기는 claimed H job 전체가 아니라 실제 시작된 H model prompt에만 적용하므로 양쪽이 서로 기다리는 deadlock을 피한다. W 준비가 끝나면 기존 목표인 Builder+늦은 Helper 동시는 유지된다. 이 admission 변경 역시 자동화 빌드와 source review만 통과했으며 live H-first→Builder 검증 전이다. Focus의 `activeChatExecution` 포인터만으로 두 built-in ChatAgent가 반드시 직렬화된다고 주장하지 않는다. 현재 H Helper/Analyst 상호 직렬화는 shared state 경합을 줄이려는 adapter의 보수적 선택이다.

부모/평가자가 W 한 창을 reload한 뒤 같은 extension-host PID에서 feature Inspector의 모든 flag OFF·safe=true를 다시 확인했다. 새 cloud barrier가 들어간 **무모델** H pair도 `PREFLIGHT_PASS window=4 sessions=2 memoryDefaults=true denyAll=true catalogSafe=true shellIntrospectionTags=2 analystHaiku=true modelTurns=0`로 실측됐다. 이어 저장 Episode를 UI에서 한 번 재시도하자 Analyst native turn은 18:13:31→41 UTC, 자동 재시도는 18:13:44→56 UTC에 각각 정상 terminal이었다. 즉 기존 `fetch_cloud_config` 알림에 의한 즉시 abort는 이 두 turn에서 재현되지 않았다. 하지만 결과는 두 차례 모두 `ANALYST_INVALID_RESULT`였다. 원문을 출력하지 않는 shape metadata와 소유 H 저장소의 key/type 검사에서 두 JSON은 각각 Proposal 2·3개 모두 `concept.proposedCanonicalName`만 있고 **필수 `concept.originalExpression` key 자체가 없음**을 확인했다. Core의 거절은 유효하며 이 Episode에서 새 Evidence 수락을 주장하지 않는다. Canonical prompt를 v1.0.3으로 올려 직접 USER 표현을 필수 문자열로 넣거나 근거 없으면 Proposal을 버리도록 명시하고, 마지막 native transport 지시에도 같은 일반 계약을 추가했다. 합성 fixture의 strict-schema 경계는 3/3 통과했으나 v1.0.3 실제 모델·Core 결과는 다음 turn 전까지 미검증이다.

### v1.0.3 실제 Analyst와 두 번째 개선 Task

Planner는 새 E 프로젝트의 긴 title 110자에 고정 접미사 12자를 더해 `builderTaskSchema.title`의 120자 제한을 넘겼고, `FINAL_UPGRADE_PLAN_INVALID`를 반환했다. Domain planner가 Task title만 상한 안에서 만들고 전체 user goal은 보존하도록 고쳤다. Domain 23/23, panel 17/17, Node 24.19.0의 전체 build를 통과한 뒤 기존 SQLite와 W를 유지하며 실험 전용 backend를 graceful 재시작했다. 데이터 quick_check는 `ok`였고 원본 repository는 clean이었다.

같은 한 창에서 무모델 Inspector/Pair를 다시 통과한 뒤 저장된 H4 Episode를 UI에서 재시도했다. Evidence Analyst v1.0.3의 실제 모델 결과는 Core strict schema와 정책을 통과해 Proposal 3개를 만들었다. Core는 `JUSTIFIED_DECISION/STRONG/INDEPENDENT` 한 건을 `VALID_USER_EVIDENCE`로 수락하고 Concept State를 `DEMONSTRATED`로 올렸으며, `REPHRASE/MEDIUM` 두 건은 `OVERSTATED_MAXIMUM_STATE`로 기각했다. 수락 Proposal의 `USER_MESSAGE` reference는 저장된 Episode의 실제 USER Event ID와 일치하고, 표시된 근거 문구도 그 Event의 redacted excerpt에 존재한다. 이 USER Event는 **평가자가 합성으로 입력한 것**이며 실제 학습자 이해의 증거라고 일반화하지 않는다.

같은 E lineage의 두 번째 개선 Task가 생성돼 `ACTIVE`가 됐다. Builder는 현지 달력 날짜와 `Asia/Seoul` 고정 날짜 사이의 실제 제품 선택을 Core의 `request_user_decision`에 한 번 제출했고, persistent receipt는 envelope decode→Core request→`isError=false` result를 각각 확인했다. Core Task는 Decision 대기로 `BLOCKED` rev3가 됐다. Core card의 추천은 기기 현지 날짜이며, 다른 option은 전 기기에 동일한 한국 날짜를 적용하는 것이다. 첫 E Builder에서 실패한 네 Decision의 원인은 당시 계측만으로 특정하지 못했으므로, 이 두 번째 성공으로 첫 실패 원인을 소급해 단정하지 않는다.

Decision 대기 중 Helper의 새 질문은 실제로 답했고 personalization trace는 `EVIDENCE_AWARE`였지만 basis는 기존 `OBSERVED` Evidence 두 개였다. 방금 수락한 `DEMONSTRATED` Evidence는 이 trace에 포함되지 않았다. 따라서 **새 수락 근거가 다음 답변에 반영됐다는 제품 기준은 아직 미검증**이다. 고정 한국 날짜를 선택하고 이유를 제출하는 UI 동작은 자동 승인 검토에서 “사용자가 직접 승인하지 않은 중대한 제품 동작 결정”이라는 이유로 거절됐다. 해당 UI 명령은 E의 0700 생성 W에 묶인 실험 SQLite에 resolution·Task 재개·Event/audit·Analyst job을 기록하며, 즉시 생성 앱 코드나 권한 설정을 바꾸지 않는다고 source/read-only metadata로 확인했다. 별도 API나 다른 option으로 우회하지 않고 같은 UI 동작의 안전성 검토를 기다린다. 지금은 Decision 미해결, 후속 Builder 구현·브라우저 회귀 결과 없음으로 기록한다.

같은 UI 선택은 E가 synthetic·private workspace이고 `UI_RESOLVE_DECISION`이 앱 파일이나 권한을 즉시 바꾸지 않는다는 근거를 제시한 뒤에도 자동 검토에서 다시 거절됐다. 이유는 여전히 **실제 사용자가 직접 승인한 제품 동작 선택으로 인정되지 않는다**는 것이다. E Task는 `BLOCKED`와 원 Decision card를 유지하며, 다른 API·다른 option·Builder 위임으로 선택을 우회하지 않는다. 사용자가 잠든 동안에는 추가 승인을 요청하지 않고 독립 검증을 이어 간다.

H5 질문을 묶은 Analyst는 다른 `JUSTIFIED_DECISION/STRONG/INDEPENDENT` Proposal을 `DEMONSTRATED`로 수락했다. 그러나 USER 원문은 로컬 날짜와 한국 고정 날짜의 차이를 **설명해 달라고 요청하고**, 확인된 코드와 미검증 추론을 구분해 달라는 질문이었다. Analyst는 이 요청 자체를 사용자가 이미 독립적으로 사실과 추론을 판단했다는 증명으로 과대해석했다. Core가 `VALID_USER_EVIDENCE`로 수락한 row는 삭제·교체하지 않는다. 이는 질문·카드 클릭만으로 이해 상태를 올리지 않는 제품 불변식의 **실측 실패**이며, 다음 personalization에도 잘못된 DEMONSTRATED basis가 섞일 수 있다. 합성 USER라는 한계와 별도로 semantic evidence 판정 자체를 고쳐 다시 평가해야 한다.

Personal Need를 비운 새 F 학습 goal로 Discovery를 시작하자 Core는 E의 실제 H4 수락 Evidence와 위 H5 오수락 Evidence를 포함해 `EVIDENCE_AWARE` basis 5개를 만들었다. 새 F trace가 H4 `evidence_02f8fa39`/`concept_9219df59`를 `DISCOVERY_TIE_BREAK`으로 포함한 것은 DB와 `createDiscoveryEphemeralContext()` 전달 경로로 확인했다. 다만 H5 오수락도 포함되므로 이 새 Discovery를 정당한 개인화 PASS로 보지 않는다. 실제 생성된 Discovery native profile은 canonical v1.3.2이며 후보 10개는 서로 다르지만 연습용 도구·라이브러리가 많아 브리프의 “실제 프로그램 먼저” 품질도 별도 개선 대상이다.

F의 선택 후보를 실제 마크다운 문서 작업대로 다듬은 뒤 만든 첫 Spec에도 메모이제이션 체험과 cache-hit 시각화가 제품 목적·핵심 범위로 남고, `Map`/`WeakMap`이나 cache key 같은 일상 구현 세부가 예상 사용자 Decision으로 열거됐다. 부모/평가자가 문서 작성·미리보기라는 실제 목적과 두 기능, 대시보드·외부 API·업로드 제외, Node 24 조건으로 Spec rev2를 다시 다듬었다. rev2에도 “무효화할 입력 선택”이 예상 Decision으로 남았으나 텍스트와 렌더링 옵션을 함께 반영해야 한다는 정확성 조건상 실제 양자택일은 아니다. `learning-spec` 계약이 `expectedDecisions`에 최소 한 항목을 요구하는 구조적 제약도 확인했다. 이 계약이나 저장된 Spec을 검증용으로 우회하지 않고, Builder에게 의미 있는 제품 분기만 Core Decision으로 요청하도록 맡긴다. 이는 Spec 생성 품질의 미해결 제약이며 F Builder의 실제 동작은 아직 별도 판정 대상이다.

H 취소/오류 후 역할 수명 개선을 먼저 source·자동화로 준비했다. 소유 H prompt의 abort 뒤 `stopReason=cancelled`가 실제 terminal로 돌아오고 도구/권한 이상이 없을 때만 같은 H 세션을 재사용한다. 빈 응답·prompt 전 취소 등 명확히 역할 로컬인 실패는 그 역할만 닫고 다른 H를 후속 attestation 후 유지한다. RPC timeout, 알 수 없는 stopReason, 도구·카탈로그·권한 이상은 pair 전체를 계속 닫는다. 부분 pair에서 실패한 역할과 새 Builder 준비는 idle restart 전까지 fail-closed한다. 이 변경은 Panel 19/19, typecheck/bundle, lint·format 및 독립 source 리뷰를 통과했고, **뒤의 F 두 번째 Builder turn에서 확인된 취소·같은 H 재질문을 실제 검증했다**. 미확인 timeout과 역할 로컬 실패 후 peer 유지의 live 효과는 아직 별도 검증 전이다.

H5 오수락에 대해 Evidence Analyst canonical prompt를 v1.0.4로 올려 **설명·비교·사실/추론 구분을 요청한 문장**과 사용자가 직접 한 주장·이유·예측·선택을 분리했다. 질문 안의 실제 사용자 주장은 보존한다. Native Analyst transport 0.1.2의 마지막 형식 지시에도 같은 일반 경계를 넣었다. 합성 negative/positive fixture는 요청만 있는 Episode의 빈 Proposal, 직접 예측, 이유 있는 실제 선택을 구분한다. Discovery canonical prompt v1.3.3은 연습용 개념 도구보다 독립적으로 쓸 수 있는 프로그램 가치를 우선하도록 일반 평가 규칙을 보강했다. 새 prompt/eval이 통과해도 기존 H5 오수락과 F trace 오염을 고치지는 않는다.

F Spec 시작 전, 세 변경을 함께 Node 24.19.0에서 build·panel bundle·eval 29/29·panel 19/19·lint·format으로 검증하고, 모든 실행 job이 terminal인 것을 확인해 기존 backend를 graceful 재시작했다. 새 instance에서도 같은 port·SQLite를 유지하고 DB quick_check `ok`, E seq2 `BLOCKED`, Analyst job `SUCCEEDED` 32건을 재확인했다. 부모가 한 창 W를 reload하고 Inspect/Pair를 다시 통과한 뒤 F Spec·Builder와 취소 재질문을 실측해야만 기능 효과를 판정한다.

### Fresh F 실제 Builder와 Helper 취소·재질문

F의 첫 Builder job을 생성할 때 backend가 새 H 디렉터리를 0700으로 준비했고, worker 기록은 19:10:11 UTC Builder claim → 19:10:14 두 H 보호 세션 준비 → 19:10:15 후행 W barrier attestation → Builder 모델 시작 순서를 보였다. Builder는 `src/render/options.ts`, `renderer.ts`, `workbench.ts` 및 웹 UI·서버·테스트 파일을 W 안에 실제 작성했다. 그러나 첫 native Builder가 `end_turn/SUCCEEDED`여도 Core receipt에는 `get_builder_task`, `start_task`, `update_build_context` 두 번까지만 있고 `complete_task`는 없었다. Core Task가 `ACTIVE rev2`, completion report가 0인 상태에서 UI `GENERATED_RESULT_NOT_READY`는 정확한 실패다. 생성 결과 descriptor만으로 Core 완료를 대체하지 않는다.

첫 구현에는 확정 Spec에서 제외한 cache badge/stats가 UI에 들어갔고, `marked`의 HTML을 `innerHTML`에 바로 넣었다. 생성 앱의 실제 `marked` 호출을 읽기 전용으로 확인하니 입력의 `<script>`와 `onerror` 속성이 모두 출력에 남았다. 부모/평가자는 임의 Core 완료를 만들거나 코드를 직접 패치하지 않고, **같은 F Task를 두 번째 Builder native turn으로 재개**해 완료 검증, Spec 밖 대시보드 제거, HTML 안전 처리와 회귀 테스트를 요청했다. 두 번째 turn의 첫 regex 기반 `sanitize.ts`는 `j&#97;vascript:` URL을 그대로 남기는 우회가 읽기 전용 문자열 테스트로 재현돼 보안 수정 PASS가 아니다. 이 상태에서 첫 F Task의 Core 완료와 앱 실행은 안전성 판정과 분리한다.

두 번째 Builder가 실제 W 파일을 읽고 수정하는 동안 19:18:07 UTC 첫 Helper를 시작해 부모/평가자가 UI에서 중지했다. 19:18:15 worker는 소유 H `session/prompt`의 terminal `cancelled`를 받은 `NATIVE_H_CANCELLED_CONFIRMED`와 `BUILTIN_H_CANCEL_CONFIRMED_REUSABLE`을 기록했다. Builder의 read/search 권한 ACK는 취소 전후 이어졌다. 19:19:00 두 번째 Helper 질문은 H pair를 다시 준비하지 않고 시작해 19:19:25 `AGENT_ENDED_HELPER`로 완료됐다. 그 H 답변 중 Builder W write ACK가 19:19:10/15/22에 발생하고, 뒤 19:19:30/38에도 이어졌다. 같은 Kiro process log에는 취소 시점 뒤 새 `session/new`가 0건이었다. 따라서 **확인된 취소 뒤 같은 H 세션 재질문과 실제 Builder 병행 작업**은 이 F turn에서 관측됐다. 취소된 첫 답의 부분 출력은 완료 답변·Evidence로 세지 않는다. 두 번째 답의 내용 정확성, 안전 수정과 브라우저 동작은 별도 검증 대상이다.

두 번째 F Helper 입력은 문서 내용은 같고 줄바꿈 옵션만 바뀔 때 cache key에 무엇이 들어가야 하는지, 실제 코드와 미검증 내용을 구분해 설명해 달라는 **질문만** 포함했다. UI에서는 Helper가 실제 `cacheKey` 구현을 언급했고, 자동 Analyst v1.0.4의 19:19:29 UTC job은 정상 `SUCCEEDED`였다. Core 저장소에서 해당 Helper Episode는 `ANALYZED`, F project의 Evidence Proposal·Decision·accepted Evidence는 모두 **0건**이었다. 적어도 이 H5와 유사한 요청형 질문은 사용자 이해를 새로 수락하지 않았으므로 v1.0.4의 보수적 live regression은 통과했다. 기존 E H5 오수락 및 F Discovery trace의 오염 기록은 그대로 남으며, 다른 질문·직접 주장에 대한 의미 판정 정확성은 추가 평가 대상이다.

그 다음 같은 Builder turn 도중 평가자는 이전 Helper 설명에 의존함을 명시하면서 “줄바꿈 옵션을 바꾸면 다른 key가 돼 재계산하고, 원래 옵션으로 돌아왔을 때 그 entry가 LRU에 남았다면 재사용할 수 있으니 전체 cache 삭제는 필요 없다”는 직접 예측을 합성 USER로 입력했다. 세 번째 Helper는 19:22:15 UTC에 답을 마쳤고 Analyst v1.0.4는 19:22:30 정상 종료했다. 서로 다른 개념의 `PREDICTION/MEDIUM/LIGHT_HINT/EXPLAINED` Proposal 두 건은 Core가 수락해 `EXPLAINED`까지만 지지했고, `JUSTIFIED_DECISION/MEDIUM/LIGHT_HINT/DEMONSTRATED` 한 건은 `OVERSTATED_MAXIMUM_STATE`로 기각했다. 이 live 결과는 직접 주장과 질문만 있던 이전 turn을 구분하고, 이전 설명에 의존한 내용을 독립적인 강한 이해로 올리지 않은 범위의 근거다. 다만 수락된 LRU Proposal의 `originalExpression`과 evidence excerpt는 H3 USER Event의 정확한 부분문자열이 아니라 **의미상 유사한 바꿔쓰기**였다. 첫 cache-key Proposal만 두 문자열이 USER Event에 정확 포함됐다. 두 수락의 source conversation/message ID는 H3 USER Event와 일치하지만, Core가 copy 요구를 강제하지 못한 이 직접 인용 provenance 결함을 PASS로 덮지 않는다. H3는 앞선 H2와 별도 Core conversation이며, 이전 답변과의 관계는 H3 USER가 “방금 설명을 바탕”이라고 명시하고 동일 native H session을 재사용했다는 범위까지만 확인된다. 합성 입력과 한 사례의 한계도 있다.

이 결함에 대해서는 Domain Evidence 판정이 인용된 직접 `USER_MESSAGE`에 `originalExpression`과 evidence excerpt 두 문자열이 각각 정확한 부분문자열인지 검사하는 좁은 gate를 격리 source에 추가했다. 기존 F 수락 행과 Concept State는 변경하지 않았다. Node 24의 unit 82/82, integration 260/260, typecheck와 format 검사가 통과했다. 뒤의 data-preserving 재시작으로 새 backend에 적용했지만, **향후 live Evidence가 이 gate로 기각되는지는 미검증**이다.

같은 변경 묶음에서 Core Helper context는 기존 개념명·질문 어휘 매칭 뒤 남은 슬롯에 현재 Task·직접 선행 Task의 같은 Project `USER_UNDERSTANDING` accepted Evidence를 `HELPER_TASK_USER_EVIDENCE_CONNECTION` 근거로 선택할 수 있게 했다. 이 fallback 자체가 질문 의미와 직접 연관됐다고 보증하지는 않는다. 질문이 명시한 code 파일명·경로는 최대 세 excerpt의 우선순위에 반영한다. 과거 E H5 오수락 Evidence를 DB에서 삭제하거나 재판정하지 않았으며, 이 새 선택 규칙이 해당 행을 자동으로 정화한다고 주장하지 않는다. 새 backend에서 실제 Helper 답변이 관련 근거를 사용하고 불필요한 근거를 배제하는지는 다음 UI 실측 대상이다.

두 번째 Builder turn에서 Core는 19:21:15 UTC Task를 `COMPLETED rev3`로 만들고 completion report를 한 건 기록했다. report의 typecheck/build/test/smoke 및 네 acceptance 항목은 모두 `PASSED`였다. Native turn은 19:23:26까지 계속됐지만, 완료 뒤 Builder write ACK와 source 파일 mtime 증가는 **0건**이라 사후 코드 수정으로 검증 결과가 무효화됐다고 주장하지 않는다. 다만 완료 당시 regex sanitizer의 entity-encoded `javascript:` 우회가 확인된 만큼 **Core 완료와 기존 회귀 테스트의 PASS는 HTML 안전성 보증이 아니다**. Completion report는 세 Spec deviation을 적었고, 집계 dashboard는 제거했다고 쓰면서 per-render cache badge는 학습 신호라며 남겼다. 이것이 확정 Spec의 제외 범위와 실제로 일치하는지는 부모의 UI 검토가 필요하다. 부모는 생성 결과를 브라우저에서 실행·검증하고 필요한 안전 수정을 후속 Task로 요청했다.

부모/평가자가 UI의 완료 결과 실행으로 실제 루프백 웹 앱을 열고 합성 Markdown을 입력했다. 줄바꿈 OFF·heading depth 2에서 줄 병합과 깊은 제목의 paragraph 표시를 확인한 뒤, depth 6·줄바꿈 ON으로 되돌리자 원래 미리보기와 cache 재사용 표시가 나타났다. 이는 **문서 편집·옵션 조정·캐시 재사용의 브라우저 기능 실측 PASS**다. 악성 HTML을 브라우저에서 실행하거나 링크를 클릭하지 않았고, 별도 문자열 재현에서 드러난 sanitizer 우회가 남아 있으므로 안전성 PASS나 공개 배포 준비 완료를 뜻하지 않는다.

평가자는 UI에서 후속 안전 개선을 새 F Task로 준비했다. Core 저장소에서 F seq2는 19:28:42 UTC에 `ACTIVE rev2`가 됐고, 요청 범위는 검증된 HTML sanitization 경계와 기존 기능 회귀 확인이다. Builder는 19:29:38 UTC 실제 Core `PRODUCT_BEHAVIOR` Decision을 요청했다. 선택지는 DOMPurify를 써서 안전한 raw HTML을 지원하거나 parser에서 raw HTML 자체를 비활성화하는 것으로, 사용자 결과가 다른 제품 분기다. E의 유사한 사용자 선택은 자동 승인 검토에서 두 번 거절됐고 현재 사용자가 직접 승인하지 않았으므로, 부모/평가자는 이 F 선택을 제출하거나 다른 경로로 우회하지 않았다. Native Builder turn 종료 뒤에도 Decision은 `REQUESTED`, Task는 `ACTIVE rev2`로 남았다. E의 Task처럼 `BLOCKED`로 바뀌었다고 말하지 않으며, 후속 안전 수정·Core 완료·악성 입력 회귀는 미검증이다. 생성 앱 코드를 평가자가 직접 수정하거나 기존 완료·Evidence 기록을 변경하지 않았다.

Analyst v1.0.4 의미 경계를 비교할 별도의 순차 평가 명령도 격리 source에서 준비했다. 합성 Episode 세 개에 v1.0.3 역패치 재구성본과 v1.0.4, IDE 설정에서 확인한 Haiku 4.5와 Sonnet 4.5를 교차해 최대 12개 turn으로 제한한다. v1.0.3 해시는 수정 전 독립 보관본이 아니라 **명시적 역패치로 사후 재구성한 원문**의 해시다. 각 cell은 새 보호 H 세션·cloud barrier·deny와 memory/hook gate를 거치며 Core Evidence를 쓰지 않는다. 결과 artifact는 식별된 상태·schema·source 정확성 등 metadata만 0600 파일로 남기고 응답 원문을 넣지 않는다. Kiro 자체 session history에는 합성 prompt와 응답이 저장될 수 있다. 30초는 취소를 요청하는 soft budget이고 native RPC는 최대 240초까지 대기할 수 있으며, `PLAN_FINISHED`는 평가 계획을 처리했다는 뜻이지 의미 정확성 PASS가 아니다.
