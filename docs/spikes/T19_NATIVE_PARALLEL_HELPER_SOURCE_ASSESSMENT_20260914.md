# T19-N: Builder 중 Helper 응답 경로 소스 판별

2026-09-14. 범위는 격리된 `.local-experiments/kiro-native-recovery`와 설치된 macOS Kiro IDE 1.0.437 / Agent extension 1.0.794의 소스 분석 및 별도 IDE host 경로의 구현 spike다. 소스 판별·구현 단계에는 native Agent turn이나 Core mutation을 시작하지 않았다. 이후 사용자가 Kiro UI에서 Project D의 Discovery, Builder, Helper를 실행해 첫 두 창 실측을 했다. 생성 앱 코드는 Kiro Builder가 작성했으며, 설치본은 변경하지 않았다. 이전 10시간 판정에서 기록한 두 번의 Builder Core 도구 소실과 `AGENT_QUEUED_HELPER_BEHIND_BUILDER`를 출발점으로 삼는다. 제품의 통과 기준은 Helper의 Core context 조회와 답변이 Builder terminal 전에 도착하면서, Builder의 Core mutation 도구와 완료도 유지되고, Helper가 read-only를 벗어나지 않는 것이다.

변경 전 단일 Host relay는 같은 Project의 Builder와 Helper 모두 실제 생성 workspace W에서 session을 열었다. 각 config는 같은 `vibe-native-core`라는 이름에 서로 다른 run-bound stdio descriptor를 붙인다. `NativeAgentRelay.#prepareConfig`는 Helper에 `get_helper_context`만, Builder에 7개 Core 도구와 `read/write/shell`만 선언하며, `boundedCoreRole`은 이 exact config를 확인한다. Core HTTP handler 자체도 role·Project·Task·correlation 및 bearer로 묶는다. 다만 공유 pool에 Builder 바인딩 서버가 살아 있고 built-in ChatAgent에 노출되면, Core는 그 호출의 **Kiro 세션 출처**를 알 수 없으므로 Helper의 호출을 Builder 호출과 구별할 수 없다. 이 때문에 `서버 union + built-in ChatAgent + prompt만 read-only`는 혼동된 권한 호출 위험이 있고 live prompt 후보에서 제외한다.

## 격리 worktree에 준비한 별도 host spike

Project별 H는 backend가 검증한 canonical `runtime/workspaces/__vibe-native-helper-<project hash>` 직접 자식이다. H를 새로 만들 때는 mode `0700`을 사용하고 기존 H도 symlink, 비디렉터리, group/other 접근 mode 및 현재 사용자와 다른 소유자를 거부한다. 외부 요청에 H path 선택 옵션을 추가하지 않았다. 실제 Project W는 `resolveProjectWorkspace(snapshot.project, correlationId)`로 확정하며 Task/Project/correlation Core binding은 계속 W의 Core 상태를 기준으로 발급한다. Builder는 W와 기존 7개 Core 도구를 유지한다.

Helper와 해당 Project의 **모든 Evidence Analyst**는 H에서만 연다. 자동 Analyst invocation에는 `taskId`가 없으므로 Task별 H 또는 taskId 조건 fallback을 쓰면 Builder W의 MCP pool을 다시 변경할 수 있다. Helper H config는 `get_helper_context` 한 도구와 `fs_write`/`shell` deny, Analyst H config는 도구 0개와 같은 deny다. H에는 생성 앱 코드를 복사하지 않는다. Core의 Helper context 안 코드 발췌는 Application의 기존 `readCodeExcerpt(aggregate.project, ...)`가 W를 해석한다. H의 native `fs_read`가 W를 읽는 동등성은 **입증하지 않았고 이번 spike의 제공 기능이 아니다**.

Relay는 H Job을 Builder W worker의 `pendingWorkspace()` 자동 전환 대상에서 제외하고, H에서 CLAIMED Job이 있으면 다른 Helper/Analyst claim을 보류한다. H worker도 다른 Project W로 자동 전환하지 않으며, 자신의 이전 H session이 닫히기 전 새 H session을 열지 않는다. Backend는 동시에 CLAIMED인 H Job을 하나로 제한한다. 정상 단일 H worker에서는 `/complete` 뒤 `session.close()`와 active Map 삭제까지 새 poll이 끼어들지 않는다. 중복 H worker 또는 같은 bearer의 별도 caller가 있으면 `complete` 직후 claim 해제와 실제 `session.close()` 사이의 짧은 경합이 남는다. 따라서 H를 정확히 하나의 live window에서만 열고 종료·close 순서를 실측해야 한다. 일반 W 간 전환과 기존 Builder 활성 조건은 유지한다. Helper/Analyst에서 나오는 TEXT, TOOL 및 최종 응답에는 H와 실제 W 두 root를 backend에서 모두 redaction한다. Helper binding 종료 후 descriptor/handler는 폐기되고 Builder binding은 유지되어야 한다. 각 job의 native session open 시 역할·job id·숫자 `windowId`만 runtime metadata에 기록해 두 host가 서로 다른 endpoint인지 실측할 수 있다. 이 metadata에는 port, token, raw session id, 응답 내용이 없다.

이 설계는 **같은 Kiro 앱의 다른 IDE 창과 Agent host**를 사용한다. 단일 IDE host에서 두 custom Agent를 동시에 실행하는 해결책이라고 주장하지 않는다. Backend bearer를 가진 worker의 `workspace` claim 값은 worker가 로컬 single-root realpath에서 얻지만 암호학적 host 신원 증명은 아니다. 실제 H/W 창을 각각 열어 endpoint `windowId`가 다름을 확인해야 이 설치본의 host 분리를 인정할 수 있다.

실측 전에 새 Project D의 H 창을 미리 열고 worker 연결을 확인해야 한다. Helper 뒤에 자동으로 호출되는 Analyst에는 H queue 대기까지 포함한 기존 약 30초 실행 budget이 있으므로, Helper 완료를 보고서야 H를 열면 Analyst timeout 또는 재시도로 판정이 흐려진다. 이 budget을 조용히 연장하지 않는다. Worker의 Helper terminal 및 `AGENT_SESSION_CLOSED_HELPER` 뒤 Analyst claim 순서를 확인한다. Backend 및 패널 갱신은 기존 live Job이 없다는 read-only preflight 후에만 진행한다.

통과 판정은 (1) endpoint `windowId`가 서로 다르고 각 Job이 자기 root에서 claim됨, (2) Helper의 실제 `get_helper_context` Core receipt와 답변이 Builder terminal 전에 기록됨, (3) Builder의 `update_build_context`와 `complete_task`가 실제 Core receipt로 성공하며 Task가 COMPLETED, (4) 자동 Analyst가 H에서 실행되고 Builder 도구 catalog를 흔들지 않음, (5) Helper role config 및 Core handler의 read-only 경계가 유지됨이다. 어느 하나라도 빠지면 병렬 제품 동등성 PASS로 쓰지 않는다. 두 창이 하나의 Agent controller/pool을 공유하거나 W/H exact binding을 입증하지 못하면 구현을 이어가지 않는다. 이 판정은 `get_helper_context` 기반 Helper 경로에 한정하며 native file-read parity를 포함하지 않는다.

이 판별은 별도 창과 private endpoint에 의존한다. 일반 설치 profile·Windows·공식 장기 제어 계약은 여전히 미검증이며, 원본 MVP/CLI 기본 경로 변경 근거가 아니다.

## Project D 첫 두 창 실측과 패널 표시 보정

사용자가 실제 Kiro UI에서 만든 Project D `project_efc36445-7551-495f-bf4e-c66b82c871a8`의 첫 Builder/Helper pair를 확인했다. Builder W native session은 08:14:48.891 UTC에 `windowId=4`, Helper H session은 08:15:46.373 UTC에 `windowId=6`으로 열렸다. 두 창의 single-root와 worker claim은 각각 W/H였고, Helper config는 `get_helper_context` 한 도구와 write/shell deny, Builder config는 기존 Core 7개 도구였다. Helper의 실제 `get_helper_context` Core receipt는 `isError=false`였고, Helper run은 08:16:18.478 UTC `SUCCEEDED/HELPER_RECORDED`로 끝났다. 그때 Builder run과 Task는 아직 RUNNING/ACTIVE였다. Backend의 redacted transient SSE에 Helper TEXT 46개, 총 1,864자가 남아 있으며 `sort`가 원본 배열을 바꿔 등록 순서를 잃는 점과 복사 후 정렬하는 방법을 설명한다. 이 출력은 영구 보관하지 않는다.

첫 자동 Analyst는 `AGENT_SESSION_CLOSED_HELPER` 08:16:18.466 UTC 뒤 08:16:19.074 UTC H에서 claim했고 `windowId=6`이었다. Builder가 그 후에도 Core `update_build_context` 성공 receipt를 남기고 `complete_task` Core `isError=false`를 얻었다. Builder run은 08:20:26 UTC `SUCCEEDED/TURN_ENDED`, Task sequence 1은 SQLite head revision 3 `COMPLETED`였다. 완료 후 Analyst까지 해당 Project의 Analyst Job 2건 모두 `SUCCEEDED`였다. 사용자는 Kiro Builder가 만든 결과 앱을 실제 브라우저에서 열어 책 추가, 제목/등록 순서 전환, 읽음/안 읽음 필터, 빈 제목 거절을 확인했다. 이는 이 한 pair의 Core 동시성·생성 결과 검증이며 장시간 안정성이나 단일 Agent host 병렬성을 증명하지 않는다.

이 과정의 앞선 Spec turn은 bridge의 `BRIDGE_ENVELOPE_JSON_INVALID` 3회 후 Kiro UI의 실제 질문에서 검증된 오류 원인을 알려 한 번 복구했다. Builder 중에도 일부 tool update가 FAILED였고, 초기 `get_builder_task` FAILED update에는 Core receipt가 없어 Kiro catalog/transport 원인을 특정하지 못했다. 나중의 별도 `get_builder_task` Core `AGENT_RUN_SCOPE_MISMATCH`는 호출 범위 오류로 구분한다. `Tool is not available`라는 native 출력은 이 pair에서 확인되지 않았다. 최종 Core receipt가 성공했어도 이 중간 실패를 지우거나 두 창의 장기 안정성을 PASS로 확대하지 않는다.

첫 UI 관찰에서는 AX가 단일 `#stream`의 앞부분 Discovery 출력만 돌려주어 Helper run SUCCEEDED는 보였지만 답변 화면 표시를 확인하지 못했다. AX가 `<pre>`의 첫 500자만 제공하고 scroll 상태가 섞일 수 있어, 기존 화면에서 실제 답변이 없었다고 단정하지 않는다. 소스상 원래 패널은 모든 run의 TEXT/TOOL을 하나의 출력에 누적하고 종료된 Helper의 transient SSE를 History에서 재구독하지 않았다. 이를 run별·sequence별 redacted 출력 버퍼, run 선택, 최신 Helper 자동 선택, 종료 Helper SSE 재생으로 보정했다. 중복/역순 sequence와 100k 절단, Project A→B→A 및 Webview 재생성도 회귀 테스트했다. `node --test examples/kiro-panel/test/*.test.cjs` 11/11, format/lint/typecheck/panel build가 통과했고, W/H 두 extension bundle/media copy는 동일 checksum이다. **Builder terminal 뒤** W Dev Host를 reload한 다음 실제 UI에서 HELPER `SUCCEEDED` run의 전체 응답, sort mutation 및 copy/filter 설명이 보이는 것을 회고적으로 확인했다. 다음 live Helper turn에서 Builder와 겹친 동안 자동 선택·표시가 유지되는지는 별도로 실측해야 한다.

Reload 후 사용자가 Kiro UI에서 보낸 post-build Helper 질문은 평가용 synthetic USER 입력이며 실제 인간 학습자의 이해 증거로 해석하지 않는다. 질문에 기존 Evidence Trace의 canonical concept `파생 뷰`·`불변 필터링`을 명시하자 Core Helper personalization이 `EVIDENCE_AWARE`·basis 3건으로 생성됐다. 해당 Helper는 H `windowId=6`에서 `get_helper_context` Core `isError=false` 후 08:35:01 UTC `SUCCEEDED/HELPER_RECORDED`였다. 후속 Analyst는 UNKNOWN permission을 strict deny한 첫 H 시도가 약 30초 후 `NATIVE_CANCELLED_CONFIRMED`였고, 자동 두 번째 시도가 08:35:53 UTC 끝나 SQLite Job `SUCCEEDED`·attempt 2가 됐다. 이 복구를 첫 시도 성공으로 뭉개지 않는다. 사용자 UI에는 Evidence 1건 수락·1건 기각이 표시됐으므로 synthetic 설명 전체가 수락됐다고 주장하지 않는다. Core가 조건에 맞는 trace를 표시한 뒤 사용자 UI 조작으로 Project D sequence 2 Task가 08:36:12 UTC `PENDING` rev1로 만들어졌고, read-only 확인 시 active run은 없었다. 이 Task는 제목의 trim·대소문자 무시 부분 문자열 검색을 기존 필터/정렬과 결합하고 등록순서를 보존하는 좁은 개선이다. 두 번째 Builder/Helper 겹침과 진행 중 화면 표시는 아직 별도 검증이 필요하다.

Sequence 2 Builder가 08:37:13 UTC UI에서 시작했다. 초기에 `get_builder_task` Core가 `AGENT_RUN_SCOPE_MISMATCH` 2회를 반환했고 세 번째가 성공했으며, 08:38:10 UTC `start_task` Core `isError=false`로 Task가 `ACTIVE` rev2가 됐다.
