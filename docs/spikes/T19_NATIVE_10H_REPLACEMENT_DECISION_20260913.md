## 현재 판정: 순차 수직 흐름 가능, 현 단일 Host·어댑터의 동시 역할 동등성은 실패

설치된 macOS Kiro IDE 1.0.437 / Kiro Agent extension 1.0.794와 승인된 합성 Project에서는 **Kiro CLI나 별도 모델 API 없이** 내장 native Agent만으로 Discovery→Spec→실제 앱 구현·검증→Core 완료→결과 실행→Helper/Analyst Evidence→다음 개인화 및 sequence-2 개선을 완주했다. 서로 다른 A/B/C 목표의 실제 생성 앱도 브라우저에서 검증했다. 따라서 “IDE Agent로 이 기능을 수행할 수 없다”는 결론은 증거와 맞지 않는다.

반면 **현재 단일 IDE Host와 어댑터의 Builder+Helper 동시 역할 설계는 기존 CLI 흐름을 완전하게 대체하지 못한다.** 두 역할의 실행 기록은 겹쳤으나, 새 계측에서 Helper가 `AGENT_QUEUED_HELPER_BEHIND_BUILDER`를 실제로 받았다. 첫 병행 실험에서 Builder의 `update_build_context`가 “Tool is not available”로 실패했고, `complete_task` 실패는 그 턴의 Agent 자기보고뿐이다. 두 번째 병행 실험에서는 Builder의 `update_build_context`와 `complete_task` 모두 실제 native ToolCall 실패로 확인됐다. 두 실험 모두 Core Task 완료가 남았다. 설치본 소스는 같은 Host의 custom-agent 직렬 queue와 선택 session에 맞춘 공유 MCP pool 교체를 보여 주며, 이것이 실측 오류의 유력한 원인이라는 판단은 소스와 타이밍에 근거한 추론이다. 역할별 서버 이름만 다르게 하는 것으로는 선택되지 않은 서버 제거를 막지 못한다. 이는 이 버전·현 어댑터의 재현 가능한 결함이지 단일 Host나 Kiro IDE 전체의 영구적 불가능 증명은 아니다.

실무 판정은 **CLI 경로와 결정적 Core를 유지하고 native 경로를 opt-in 실험으로 두는 것**이다. 임시 회피는 Builder terminal 전 Helper뿐 아니라 Analyst 등 다른 native 역할의 `session/new`도 시작하지 않는 직렬 admission이며, 아직 구현·실측되지 않았다. 질문을 받기 위해 Builder를 명시적으로 checkpoint/일시 중지하고 Helper 뒤 재개하는 UX도 별도 설계가 필요하다. 어느 쪽이든 즉시 병렬 응답 UX는 보존되지 않고 성능 동등성은 미검증이다. 현재 Helper 240초 prompt timeout에는 queue 대기 시간까지 포함되므로 제품 설계에서는 queue 예산과 실제 실행 예산을 따로 다뤄야 한다. 완전 대체를 목표로 하면 유지되는 공식 session/MCP 제어 계약을 확인하고 active-session 서버 union과 세션별 권한 격리를 설계·검증해야 한다. Windows, 일반 설치 profile, 반복 성공률과 같은 목표의 CLI 성능 비교도 아직 없다. 원본 코드·기본 runtime·사용자 데이터는 이 판정으로 전환하거나 삭제하지 않는다.

| IDE-only replacement is demonstrably unavailable on the tested surface | A reproducible platform constraint remains after version/capability checks and supported native IDE alternatives are exhausted, with a specific failed contract or unsupported official capability. A single failed turn, private-API instability, adapter bug, time limit, or lack of Windows evidence is insufficient to prove impossibility. |
| Functional result undetermined; do not replace CLI | Any functional gate remains unverified or unreliable by the hard stop, especially Builder verification/completion, result health, recovery or repeat-goal behavior. Record the exact observed blocker and the next discriminating test. Product-readiness findings may independently remain unresolved even if this functional gate passes. |

The existing CLI/Crew path stays available throughout. “IDE-only” means no `kiro-cli`, other coding-agent CLI, external model API, or second model is used for Agent decisions. The Core/relay/MCP and package-manager commands are infrastructure, not an alternate model. `SUCCEEDED/TURN_ENDED` alone is not Task completion; Core Task/Completion Report and healthy result decide that gate. Synthetic `source.kind=USER` indicates UI provenance, not proof of real learner understanding. No accepted Evidence may come from Agent-authored code or explanation. The existing CLI path also delegates package scripts to a host shell; OS-level confinement is a shared product hardening gap unless native adds a specific regression, not a one-sided functional criterion.

Intervention accounting is separate from functional success. Candidate selection, Spec confirmation or revision, actual product Decisions, and a user-authored Final Upgrade goal are intended product interactions. Manual schema-error coaching, transport or panel source patches/reloads, regeneration after an erroneous return action, repeated command-shape correction, path-root repair, and repeated Builder resumes are troubleshooting interventions; they cannot be counted as an unattended turnkey flow. Record durations from durable run timestamps where available. There is no controlled same-goal CLI latency baseline in this spike, so a native duration alone cannot establish performance parity.
