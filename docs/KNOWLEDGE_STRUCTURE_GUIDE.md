# Knowledge 구조를 함께 이해하기

> 이 문서는 Vibe Helper의 Knowledge 구조를 처음 접하는 팀원을 위한 설명서다.
>
> 정확한 제품 요구사항은 [PROJECT_BRIEF.md](../PROJECT_BRIEF.md)와 [SPEC.md](SPEC.md), 기술 구현 기준은 [ARCHITECTURE.md](ARCHITECTURE.md)를 따른다.

## 먼저 한 문장으로 설명하면

Vibe Helper의 Knowledge 구조는 사용자가 무엇을 배웠는지 AI가 감으로 판단하는 메모리가 아니다.

**프로젝트에서 실제로 일어난 일과 사용자가 직접 보여 준 이해의 근거를 나누어 기록하고, 그 근거만으로 다음 도움을 개인화하는 구조**다.

우리에게 중요한 질문은 다음과 같다.

- AI가 어떤 코드를 작성했는가?
- 프로젝트에서 어떤 개념이 실제로 사용됐는가?
- 사용자가 그 개념을 자기 말로 설명하거나 판단에 사용했는가?
- 다음 프로젝트에서도 스스로 다시 사용할 수 있었는가?

이 질문들은 비슷해 보이지만 서로 다른 사실이다. 특히 **AI가 어떤 개념을 사용했다는 사실이 곧 사용자가 그 개념을 이해했다는 뜻은 아니다.** 이 구분이 현재 Knowledge 구조의 출발점이다.

## Knowledge는 하나의 메모장이 아니다

우리는 기억을 세 영역으로 나눈다.

```text
현재 작업 메모
    ↓
프로젝트 기록
    ↓ 중요한 장면을 묶어 분석
이해의 근거
    ↓ 검증된 규칙으로 계산
개념 장부
    ↓ 필요한 항목만 꺼내 사용
다음 Helper 답변과 프로젝트 추천
```

### 1. 현재 작업 메모

정식 이름은 `Live Project Context`다. Builder가 지금 무엇을 하고 있는지 보여 주는 최신 메모라고 생각하면 된다.

예를 들면 다음 내용이 들어간다.

- 지금 진행 중인 작업
- 현재 단계와 목표
- 최근에 바꾼 내용
- 사용자 결정을 기다리는 항목
- 현재 사용 중인 주요 개념
- 관련 파일
- 다음에 할 일

Builder는 작업을 시작하거나 방향이 바뀔 때, 새로운 개념을 도입할 때, 오류로 계획이 달라질 때, 테스트할 때 이 메모를 갱신한다.

Helper는 질문을 받으면 이 메모부터 확인한다. 메모가 오래됐거나 없다면 현재 상황을 추측하지 않고 Builder에게 갱신을 요청한다.

중요한 점은, **현재 작업 메모는 사용자의 이해를 보여 주는 근거가 아니라는 것**이다. “지금 일회용 링크를 구현하고 있다”는 사실만으로 사용자가 접근 토큰을 이해했다고 판단하지 않는다.

### 2. 프로젝트 기록

정식 이름은 `Project History`다. 프로젝트에서 실제로 어떤 일이 있었는지 시간의 흐름에 따라 남기는 기록이다.

여기에는 다음과 같은 내용이 포함된다.

- 어떤 작업을 시작하고 완료했는지
- 어떤 선택이 필요했고 사용자가 무엇을 선택했는지
- 그 선택이 실제 구현에 어떻게 반영됐는지
- Helper와 어떤 주제로 대화했는지
- 어떤 테스트가 통과하거나 실패했는지
- 관련 코드나 변경 부분을 찾을 수 있는 참조

모든 키 입력, 모든 파일 내용, 모든 터미널 출력을 계속 저장하지는 않는다. 의미 있는 사건만 고르고, 관련된 사건들을 하나의 장면으로 묶는다. 이 장면을 현재 문서에서는 `Episode`라고 부른다.

예를 들어 다음은 하나의 장면이 될 수 있다.

```text
Builder가 파일 공유 링크의 만료 시간이 필요하다고 보고함
→ 사용자에게 10분과 24시간 중 어떤 정책을 쓸지 요청함
→ 사용자가 Helper에게 차이를 질문함
→ 사용자가 이유를 붙여 10분을 선택함
→ Builder가 선택을 적용하고 테스트함
```

우리는 메시지 하나가 생길 때마다 사용자를 분석하지 않는다. 이런 장면이 끝난 뒤 한 번만 살펴본다. 이렇게 해야 불필요한 분석, 비용, 개인정보 수집을 줄이면서도 앞뒤 맥락을 함께 볼 수 있다.

### 3. 개념 장부

정식 이름은 `Concept Ledger`다. 한 사용자의 여러 프로젝트에 걸쳐 쌓인 이해 상태를 개념별로 정리해 둔 장부다.

한 개념 항목에는 대략 다음 내용이 들어간다.

- 기준이 되는 개념 이름과 짧은 설명
- 같은 개념으로 확인된 다른 표현
- 현재 확인된 상태
- 그 상태를 뒷받침하는 근거 목록
- 아직 풀리지 않은 오해
- 이 개념과 관련된 프로젝트와 작업
- 마지막 갱신 정보

예를 들어 `Access Token`, `접근 토큰`, `일회용 링크 키`가 같은 뜻으로 쓰였다고 확인되면 하나의 개념 아래 연결할 수 있다. 하지만 비슷해 보인다는 이유만으로 자동으로 합치지는 않는다. 서로 다른 개념의 기록이 잘못 섞일 수 있기 때문이다.

개념 장부는 원문을 전부 복사해 넣는 보관함이 아니다. 자세한 근거는 별도로 보존하고, 장부에는 현재 상태와 그 상태를 만든 근거의 연결을 둔다. 그래서 나중에 “왜 이 상태가 됐지?”를 다시 따라갈 수 있다.

## 이해 상태의 네 단계

개념 장부의 상태는 네 단계다.

```text
접함 → 설명함 → 판단에 사용함 → 다른 곳에서도 사용함
```

문서와 코드에서는 각각 다음 이름을 사용한다.

| 상태 | 팀에서 이해할 의미 | 예시 |
| --- | --- | --- |
| `OBSERVED` | 프로젝트에서 그 개념이 실제로 등장함 | Builder가 만료 시간을 구현함 |
| `EXPLAINED` | 사용자가 자기 말로 원리나 결과를 설명함 | “만료 시간이 지나면 예전 링크는 사용할 수 없는 거죠”라고 설명함 |
| `DEMONSTRATED` | 현재 프로젝트의 판단이나 문제 해결에 사용함 | 공용 PC 사용 위험을 이유로 10분 만료를 선택함 |
| `TRANSFERRED` | 다른 기능이나 프로젝트에서 직접적인 유도 없이 다시 사용함 | 다른 프로젝트의 비밀번호 재설정 링크에도 만료 정책을 스스로 적용함 |

이 단계는 점수나 시험 등급이 아니다. Helper가 어디서부터 설명하면 좋을지, 과거 어떤 경험을 연결하면 좋을지 정하는 참고 정보다.

그래서 다음 원칙을 지킨다.

- 상태가 낮다고 Builder가 더 나쁜 코드를 작성하지 않는다.
- 상태가 높아도 Helper를 숨기지 않는다.
- 사용자에게 근거 없는 이해도 퍼센트를 보여 주지 않는다.
- 프로젝트 추천에서는 사용자의 흥미와 실용성이 우선이고, 개념 장부는 보조 정보로만 사용한다.

## 무엇을 이해의 근거로 인정하는가

우리는 이해를 보여 주는 자료를 `Evidence`, 즉 근거라고 부른다.

근거가 될 수 있는 행동은 다음과 같다.

- 사용자가 자기 방식으로 다시 설명함
- 결과를 미리 예측함
- 이유를 들어 실제 선택을 내림
- 문제 해결이나 구현 방향에 개념을 적용함
- 새로운 상황에서 같은 원리를 다시 사용함

반대로 다음은 그 자체만으로 이해의 근거가 아니다.

- “네”, “ㅇㅋ” 같은 확인 응답
- 빠른 설명 카드 클릭
- AI가 방금 한 말을 그대로 반복함
- AI가 작성한 코드
- Builder의 추천을 이유 없이 그대로 수락함
- 단순히 질문을 한 사실

질문은 관심이나 혼란을 보여 줄 수 있지만, 질문했다는 사실만으로 이해 상태를 올리지는 않는다.

근거를 볼 때는 행동의 종류뿐 아니라 다음도 함께 본다.

- 얼마나 분명한 근거인지
- 사용자가 스스로 한 것인지
- Helper가 조금 힌트를 줬는지
- 답을 거의 알려 준 뒤 따라 한 것인지
- 어떤 프로젝트와 장면에서 나온 것인지

즉 같은 문장이라도 앞에서 답을 모두 알려 준 뒤 따라 한 것과, 사용자가 먼저 자기 말로 설명한 것은 다르게 다룬다.

## AI가 바로 상태를 바꾸지 않는 이유

완료된 장면은 Evidence Analyst가 읽는다. Analyst는 “이 발언은 이런 개념에 대한 강한 근거로 보인다”처럼 후보를 제안한다.

하지만 Analyst가 개념 장부를 직접 수정하지는 않는다. 제안은 `Core`라고 부르는 검증 프로그램이 다시 확인한다.

Core는 다음을 검사한다.

- 정말 사용자가 만든 발언이나 행동인가?
- 해당 프로젝트와 장면에 실제로 존재하는 자료인가?
- 같은 제안이 중복 제출된 것은 아닌가?
- 근거에 비해 상태를 지나치게 높게 제안하지 않았는가?
- 현재 합의된 상태 변경 규칙에 맞는가?

검사를 통과한 근거만 채택되고, 정해진 규칙이 상태를 계산한다. 같은 근거와 같은 규칙을 넣으면 언제나 같은 결과가 나와야 한다.

이 구조를 택한 이유는 AI의 의미 해석 능력은 활용하면서도, AI 한 번의 자신감 있는 판단으로 사용자 상태가 마음대로 바뀌지 않게 하기 위해서다.

## 오해는 별도 문제로 다룬다

`MISCONCEPTION`은 이해 상태의 다섯 번째 단계가 아니다. 해결 여부를 추적하는 별도 문제로 기록한다.

예를 들어 사용자가 “접근 토큰이 파일 내용을 암호화해 주는 거죠?”라고 말한다면 다음처럼 처리할 수 있다.

- 맞는 부분과 틀린 부분을 문장 단위로 나눈다.
- 틀린 부분은 오해 가능성으로 기록한다.
- 기존 이해 상태를 한 번에 낮추지 않는다.
- 이후 사용자가 차이를 정확히 설명하거나 판단에 적용하면 해결 근거를 연결한다.

정정 설명을 들었다는 사실만으로 오해가 해결됐다고 판단하지도 않는다. 이후 사용자의 설명이나 행동에서 확인해야 한다.

## 전체 예시로 다시 보기

Campus Drop 프로젝트에서 사용자가 일회용 파일 공유 링크를 만든다고 가정해 보자.

1. Builder가 접근 토큰과 만료 시간을 코드에 사용한다.
   - 프로젝트에서 이 개념이 등장했다는 사실은 기록할 수 있다.
   - 아직 사용자가 이해했다고 보지는 않는다.

2. 사용자가 Helper에게 “토큰은 공용 PC에 남은 링크를 아무나 쓰지 못하게 하는 임시 비밀번호 같은 건가요?”라고 묻는다.
   - Helper는 맞는 대응과 비유의 한계를 설명한다.
   - 질문 자체만으로 상태를 올리지는 않는다.

3. 사용자가 “그러면 학교 공용 PC에서는 노출 위험이 있으니 24시간보다 10분이 낫겠어요”라고 선택한다.
   - 사용자가 개념을 실제 제품 판단에 사용한 강한 근거 후보가 된다.

4. 분석 담당 AI가 이 장면을 보고 근거를 제안한다.
   - AI는 제안만 하고 상태를 직접 바꾸지 않는다.

5. Core가 출처와 규칙을 확인한 뒤 근거를 채택한다.
   - 조건을 만족하면 `DEMONSTRATED`, 즉 판단에 사용한 상태까지 뒷받침할 수 있다.

6. 나중에 다른 프로젝트에서 사용자가 비밀번호 재설정 링크에도 만료 시간을 스스로 적용한다.
   - 이전과 다른 상황에서 독립적으로 다시 사용했다면 `TRANSFERRED`의 근거가 될 수 있다.

7. 다음 Helper는 이 기록을 보고 처음부터 교과서식 정의를 반복하는 대신, Campus Drop에서 사용했던 임시 링크 경험과 현재 상황의 차이부터 설명할 수 있다.

이것이 우리가 원하는 개인화다. 사용자를 시험하거나 자동 교육 과정을 강요하는 대신, 실제 개발 경험을 다음 도움에 연결한다.

## 예전 Knowledge Debt 아이디어와의 차이

초기에는 사용자가 모르는 개념을 `Knowledge Debt` 목록처럼 보여 주는 방안도 있었다. 현재 합의에서는 이것을 핵심 저장 구조나 사용자 경고로 사용하지 않는다.

이유는 간단하다. 현재 프로젝트에 필요하지 않은 개념을 모른다는 것은 빚이 아니고, 모르는 항목을 길게 보여 주는 경험은 실제 개발보다 교육 관리가 앞에 나오기 쉽기 때문이다.

필요하다면 나중에 다음 차이를 계산할 수는 있다.

```text
이번 프로젝트에서 사용자가 직접 다룰 필요가 있는 수준
- 근거로 확인된 현재 상태
```

하지만 이 계산은 이번 프로젝트의 학습 중심 범위에만 적용한다. Builder가 주로 맡기로 한 기술이나 이번 프로젝트에서 제외한 기술까지 사용자의 부족함으로 계산하지 않는다.

## 개인화할 때도 최소한만 꺼낸다

Helper나 Discovery가 전체 프로젝트 기록과 전체 개념 장부를 매번 읽지는 않는다.

Helper는 현재 질문과 관련된 작업, 결정, 개념, 과거 장면과 코드 참조만 받는다. Discovery도 새 프로젝트 후보를 고르는 데 관련 있는 과거 경험만 참고한다.

이렇게 하는 이유는 다음과 같다.

- 관련 없는 과거 정보가 답변을 흐리지 않게 한다.
- 불필요한 개인정보 노출을 줄인다.
- 분석 비용과 응답 지연을 줄인다.
- 오래된 기록 하나가 모든 추천을 지배하지 않게 한다.

## 저장과 안전 원칙

기록은 기본적으로 사용자 컴퓨터 안의 로컬 데이터베이스(SQLite)에 저장한다.

- 비밀번호, 토큰과 같은 민감 정보는 저장 전에 가린다.
- 코드 전체보다 관련 파일 경로, 변경 부분과 필요한 일부 내용을 중심으로 참조한다.
- 사용자의 원문 근거와 AI가 만든 설명·코드의 출처를 구분한다.
- 분석이 실패해도 이미 완성된 코드와 프로젝트 기록은 없애거나 되돌리지 않는다.
- 제안된 근거와 최종 채택·거절 결과를 함께 남겨 나중에 판단 과정을 확인할 수 있게 한다.

## 팀원이 작업할 때 꼭 지킬 경계

Knowledge 관련 기능을 구현하거나 수정할 때 다음을 확인한다.

- Builder가 사용한 개념을 곧바로 사용자 이해로 기록하지 않는다.
- Helper와 Analyst가 개념 상태를 직접 수정하게 만들지 않는다.
- 사용자의 짧은 확인이나 카드 클릭만으로 상태를 올리지 않는다.
- 직접 유도된 답변을 독립적인 이해로 취급하지 않는다.
- 한 번의 틀린 답으로 기존 상태를 자동으로 낮추지 않는다.
- 오해를 상태 단계가 아니라 해결 가능한 열린 문제로 둔다.
- 비슷한 개념 이름을 불확실한 상태에서 자동으로 합치지 않는다.
- 전체 대화나 저장소를 기본 입력으로 넘기지 않는다.
- Builder 지원 범위의 기술을 필수 학습 목표로 계산하지 않는다.
- 상태나 퍼센트보다 실제 근거를 사용자가 확인할 수 있게 한다.

## 마지막으로 기억할 것

이 구조의 목적은 사용자를 평가하는 것이 아니다.

사용자가 실제로 서비스를 만드는 흐름을 방해하지 않으면서, **이미 직접 설명하고 판단하고 적용한 경험을 잊지 않고 다음 도움에 연결하는 것**이 목적이다.

따라서 우리가 지켜야 할 가장 중요한 문장은 이것이다.

> AI가 해낸 일과 사용자가 이해했다는 근거를 섞지 않는다.
