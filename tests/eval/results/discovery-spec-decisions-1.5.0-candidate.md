# Discovery 1.5.0 후보: Spec 예상 Decision 늘리기 (2026-10-17, 채택하지 않음)

사용자가 Windows 0.2.11을 쓰며 "예상 Decision이 나올 만한데도 Spec이 정하지 않는다"고 했다(K22). 이 Mac의 9월 말 이후 Spec 15개 중 10개, 사용자 Windows Spec 2개가 모두 0개였다. 2026-09-15 결정("Learning Spec의 예상 Decision은 없을 수 있음")과 Discovery 1.3.4 이후 문구("갈림길이 이미 보일 때만")가 Discovery를 조심스럽게 만든 것으로 보고 문구를 바꿔 시험했다. **결과는 채택하지 않았다.** 지시문은 1.4.0 그대로다.

## 방법

- 개발용 Core(`apps/local-backend` `kiro-native`, 임시 SQLite), kiro-cli 2.31.1, 제품과 같은 Discovery 모델(claude-haiku-4.5, 본선 계정).
- 처음 보는 목표 10개(사용자에게 제안한 Windows 실측 첫 발언 10개, 개인 필요·서버·클라이언트 입문·갈림길이 적은 대조군·막연한 목표 포함). `experiments/kiro-live-harness/flow.mjs`로 Discovery → 첫 번째 후보 선택(상세화) → Spec 초안까지 돌렸다.
- 판정 기준(미리 정함): 실제 갈림길 예고가 뚜렷이 늘고, 약한 질문(정답이 있는 질문, 관례가 있는 세부, 화면 모양, 같은 동작을 내는 자료구조·문법 고르기)이 Spec 10개에서 2개 이하일 때 채택한다. 예상 Decision은 Builder가 코드에 닿으면 반드시 묻기 때문이다(Steering "An expected decision from the Spec: ask it when your work reaches it").

## 결과

| 문구 | Spec | 예상 Decision | 실제 갈림길 | 약한 질문 |
| --- | --- | --- | --- | --- |
| 1.4.0(현재) | 10 | 1 | 1(학습자가 먼저 쓴 동점 처리) | 0 |
| 1차(영역마다 갈림길 확인, 흔한 안이 있어도 갈림길, MVP에 미리 정하지 않기) | 9 | 25 | 약 16 | 약 9 |
| 2차(+ 전체 2개까지, 후보가 아닌 것 명시, `AGENT_SUPPORT` 제외) | 9 | 17 | 약 13 | 4 |
| 3차(+ 제출 전 후보마다 점검) | 10 | 18 | 약 14 | 4 |

- **1.4.0:** 학습 목표가 실시간 통신·재고 DB·출석 기록이어도 0개였다. 출석부는 "연속으로 2회 이상 빠진 사람"처럼 학습자가 정할 기준을 MVP 문장에 미리 정해 넣었다.
- **실제 갈림길 예(3차):** 현재 재고만 둘지 입출고 기록을 따로 둘지, 며칠 비면 결석 중으로 볼지, 오류를 즉시 보일지 제출 때 보일지, 로딩 중 다시 누르면 취소할지 기다릴지, 같은 사진을 다시 올리면 어떻게 할지, 동점 다음 순위를 3등으로 할지 4등으로 할지, 집중이 끝나면 자동으로 휴식으로 넘어갈지. 마지막은 사용자 Windows 후속 Task에서 Builder가 실제로 물은 선택과 같다.
- **약한 질문:**
  - 1차: DELETE의 ID를 경로로 받을지 바디로 받을지, 썸네일 크기와 격자 배치, 날씨 필드 구성, 지연 시뮬레이션 길이, 객체 vs Map, 차트 데이터 형식. 7번은 동점 처리를 MVP에 정해 두고 같은 것을 다시 물었다.
  - 2차: 못 찾았을 때 404인지 빈 결과인지, 스켈레톤 vs 로딩 문구, 일시정지 뒤 이어서 갈지, 빈도를 객체로 셀지 배열로 셀지.
  - 3차: 표시할 날씨 필드, 사진 메타데이터를 어떤 형태로 둘지, 객체 vs Map, 지출 객체 구조.
  - 문구가 이미 제외한 종류(자료구조 고르기, 화면 모양, 응답 코드)인데도 Spec마다 0~1개가 나왔다. 모델(claude-haiku-4.5)이 제외 목록을 끝까지 지키지 못했다.
- **판정:** 실제 갈림길 예고는 1개에서 14개로 늘었다. 하지만 약한 질문 4개가 기준(2개 이하)을 넘었다. Builder가 이것을 물으면 퀴즈처럼 보이므로 "교육용 퀴즈를 만들지 않는다"는 원칙을 우선해 채택하지 않았다.

## 다음에 시도할 것(본선 뒤)

- Builder Steering의 예상 Decision 규칙에 "코드에 닿았을 때 관례나 내부 세부로 드러나면 직접 정하고 한 문장으로 알린다"를 넣으면 약한 예고를 Builder가 걸러 낼 수 있다. 단 K14 전 0.6.2의 "중요하지 않으면 건너뛰라"가 첫 Task에서 하나도 묻지 않는 원인이었으므로, 첫 Task 묻기 실측과 함께 본다.
- Spec 모델을 Haiku보다 큰 모델로 바꾸는 것. 크레딧과 시간 비교가 필요하다.
- 3차 문구(Learning Spec 절의 `expectedDecisions` 문장, 1.4.0 대비 바뀐 부분):

> `expectedDecisions` 필드는 항상 제출한다. 후보는 Builder가 사용자에게 묻는 실제 선택과 같은 기준으로 고른다: 이 프로젝트에서 합리적인 안이 둘 이상이고, 어느 안을 고르느냐에 따라 사용자가 얻는 것(앱을 쓰는 사람이 겪는 동작, 어떤 데이터를 어디에 남기는지, API 모양, 로그인·보안, 비용, 이후 작업이 기대는 구조)이 달라지는 갈림길이다. `LEARNER_FOCUS` 영역마다 그 영역을 만들 때 이런 갈림길이 생기는지 살피고, Spec 전체에서 가장 중요한 것부터 많아도 2개까지 실제 Decision 후보로 적어라. 흔히 쓰는 안이 있어도 사용자의 목적이나 사정에 따라 다른 안이 맞을 수 있으면 갈림길이다. 후보로 남긴 갈림길의 답을 MVP 기능 문장에 미리 정해 넣지 마라. 다음은 후보가 아니다: 답이 하나로 정해진 구현 질문, 개념을 아는지 확인하는 질문, 같은 동작을 내는 자료구조나 문법 고르기, 관례가 있는 API 세부(경로, 메서드, 상태 코드), 화면 배치·크기·스타일, 나중에 쉽게 바꿀 수 있는 세부(이름, 파일 구성), `AGENT_SUPPORT` 영역 안의 선택. 제출하기 전에 후보마다 정답이 있는 질문인지, 화면 모양을 고르는 질문인지, 코드 안의 구현 방법(자료구조, 문법, 응답 코드)을 고르는 질문인지 확인하고, 하나라도 그렇다면 그 후보를 지워라. 교육을 위한 선택지를 만들거나 개수를 채우려고 후보를 만들지 말고, 그런 갈림길이 없으면 빈 배열 `[]`로 제출하라.

## 함께 본 것

- **후보 상세화 실패:** 선택한 후보의 상세화(`ENRICH_SELECTED`)가 결과를 저장하지 않고 끝난 경우가 이 시험의 약 33번 중 4번이었다(`AGENT_RESULT_NOT_STORED`, 1.4.0에서도 2번). Spec 단계에는 저장되지 않으면 한 번 더 시키는 복구 turn이 있지만 상세화에는 없다. 패널에서는 실패로 보이고 학습자가 다시 골라야 한다. 복구 turn을 넣으려면 새 에이전트 정의와 지시문 절이 필요해 본선 뒤로 남긴다(TASKS K22).
- **크레딧:** Discovery 약 47번(실패 포함). 계정 사용량은 TASKS K22에 적었다.
