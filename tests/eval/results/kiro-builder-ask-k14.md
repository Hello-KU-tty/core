# K14 실제 Kiro 확인: Builder가 묻는 기준과 후속 Task 완료 (2026-10-12)

Steering 0.7.0과 Core의 `followUpTask`·완료 거절 메시지를 담은 Mac VSIX(0.2.7 번호의 시험 빌드, backend `5e5d217` 위 작업 트리, frontend `main` `88275f6`)를 격리 Kiro 프로필(Kiro IDE 1.2.56, 본선 계정)에 설치해 확인했다. 합성 학습자 발언이며 실제 사용자 데이터가 아니다. 폴더 신뢰 화면은 이번 대상이 아니라 K10처럼 `--disable-workspace-trust`로 띄웠고, 화면 조작 없이 probe 확장으로 세션을 만들고 발언을 보냈다. 판정은 Kiro 세션 기록(도구 호출 순서와 채팅 문장)과 Core SQLite로 했다.

## 조건

- 처음 보는 목표와 Personal Need: "REST API를 직접 만들고 데이터를 저장하는 방법을 배우고 싶어" / "우리 러닝 동아리에서 누가 언제 몇 km 뛰었는지 모아서 보고 싶어". 후보 0 "러닝 기록 웹 대시보드"를 골라 Spec을 확정했다.
- 확정 Spec: 학습 목표 "REST API 요청-응답 설계", "데이터베이스 쿼리 작성". 에이전트 담당 "프론트엔드 UI와 차트 라이브러리", "데이터베이스 스키마 관리". 제외 "사용자 인증·권한 기반 분리", "대규모 동시 처리와 캐싱". **예상 Decision 없음.** Windows 첫 턴처럼 예상 Decision이 없어도 학습 목표 영역의 선택을 스스로 찾아 묻는지가 이번 확인의 중심이다.
- 빈 폴더 `k14-ws`에 연결(개발 명령 미리 승인). 첫 발언은 Windows 실측과 같은 "만들기 시작해줘".

## Core 기록

- 첫 Task: Decision 2개, 둘 다 학습자 Builder 탭 발언이 연결돼 OPTION으로 확정·적용, Analyst 3건 SUCCEEDED, 판단 근거 Evidence `DEMONSTRATED`·`JUSTIFIED_DECISION`·STRONG 2건.
- 후속 Task(sequence 2): Decision 1개 연결·확정·적용, Analyst 2건 SUCCEEDED, 완료 보고서.
- Vibe Helper 도구가 Core에서 거절된 호출 0. Kiro 도구 호출 단계의 형식 오류(`arguments: expected object, received string`, 긴 한국어 입력을 JSON 문자열로 보냄)가 3번 있었고 모두 바로 다시 보내 성공했다(K10과 같은 Kiro 모델 동작).

## 판정

- **물을 때와 방식:** 4번의 질문이 모두 코드가 그 답을 필요로 하는 순간에 하나씩 나왔고, Task 시작 때 몰아 묻지 않았다. 예상 Decision이 없는 Spec에서도 학습 목표 영역(API 모양, 집계 쿼리)의 선택을 찾아 물었다. 관례 쪽(상태 코드 400·404, Express·SQLite 선택)은 묻지 않고 밝혔다.
- **에이전트 담당:** DB 스키마·저장 위치, 차트 라이브러리(Chart.js CDN), 수정 UI 모양을 직접 정하고 밝혔다. 0.7.0 첫 문구에서는 "제가 결정하는 영역이므로"처럼 담당을 말했고, 최종 문구에서 사라졌다.
- **후속 Task 완료:** `followUpTask`를 받은 Builder가 새 기준 키로 `finish_task`를 첫 시도에 성공했고 그 뒤에 완료를 알렸다.
- **남은 것:** 최종 문구의 확인은 6턴 하나다. 예상 Decision이 있는 Spec의 첫 턴은 이번에 나오지 않았다(Discovery가 갈림길을 비워 둠). Express·SQLite 같은 프레임워크·저장 기술을 묻지 않은 것은 "관례"로 본 판단인데, 학습 목표가 저장 방식이면 물어야 할 수 있다.
- **크레딧:** 채팅 14.73, Discovery·Spec·Analyst를 더한 계정 사용량 79.19 → 약 95.4(약 16).
